## How I work

  • Architecture before features. A screen is a weekend; the seam between data and UI is where an app rots.
  • One immutable stream per screen. If two things can disagree about state, eventually they will.
  • If a rule needs an emulator to test, the boundary is in the wrong place.
  • Release engineering is product work: signing, staged rollout, crash budget, and a rollback someone has actually rehearsed.

## Choosing the platform

Flutter is not a cheaper Android. Native is not a safer default. It is a product decision, and I make it out loud.

Native · Kotlin + Compose
When the app lives close to the OS: background work, widgets, Wear and Auto surfaces, tight camera or sensor paths — or when the domain belongs in a shared KMP module the backend team also reads.

Flutter
When one team must hold two stores on one deadline, when the design system is bespoke enough that platform widgets fight it, or when custom rendering is the product.

> What I refuse: rewriting a working native app so it looks modern on an architecture slide.

class TransactionList extends ConsumerWidget {
  const TransactionList({super.key});

  @override
  Widget build(BuildContext c, WidgetRef ref) {
    final state = ref.watch(transactionsProvider);

    return state.when(
      loading: () => const TxnSkeleton(),
      error: (e, _) => ErrorView(
        message: '$e',
        onRetry: ref.read(txnRefresh),
      ),
      data: (items) => ListView.builder(
        itemCount: items.length,
        itemBuilder: (c, i) =>
            TransactionRow(items[i]),
      ),
    );
  }
}
