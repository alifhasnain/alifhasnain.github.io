# Mohammad Alif Hasnain

Senior Mobile App Developer, Dhaka, Bangladesh. 5+ years shipping Android and Flutter to production, currently at SSL Wireless.

## How I work

  • Architecture before features. A screen is a weekend; the seam between data and UI is where an app rots.
  • One immutable stream per screen. If two things can disagree about state, eventually they will.
  • If a rule needs an emulator to test, the boundary is in the wrong place.
  • Release engineering is product work: signing, staged rollout, crash budget, and a rollback someone has actually rehearsed.

## Choosing the platform

Flutter is not a cheaper Android. Native is not a safer default. It is a product decision, and I make it out loud.

Native · Kotlin + Compose
When the app lives close to the OS: background work, widgets, Wear and Auto surfaces, tight camera or sensor paths — or when the domain belongs in a shared KMP module the backend team also reads.

Flutter
When one team must hold two stores on one deadline, when the design system is bespoke enough that platform widgets fight it, or when custom rendering is the product.

> What I refuse: rewriting a working native app so it looks modern on an architecture slide.

## Easy Merchant, built twice

Easy Merchant shipped first as a native Android app, then again in Flutter. The whole product came across — payment acceptance, the digital ledger, bill recharge, KYC, cards — not a subset renamed as parity.

The port ran with AI agents working against an enforced set of project rules: one state pattern, one networking path, one place for dependency injection. Those rules are what made an agent-assisted migration reviewable instead of a pile of plausible code.

cashbaba-sdk.md

## Built for a hostile client

A payment SDK that runs inside merchant apps I do not control, on devices I cannot trust. Transport, on-device storage and the shipped build artifact are each treated as an attack surface rather than an implementation detail.

The governing constraint
A deliberately narrow public façade over self-contained flows; every session timeboxed to a server-issued token; no payment data left on the device once a flow closes.

PIN entry, OTP and liveness checks stay inside the SDK, so an integrator never handles them.

//OPEN SOURCE

falconer

A Chucker-style HTTP inspector for the Dio client. Add one interceptor and every request becomes inspectable on the device — method, URL, headers, bodies, timing, status — with search, JSON pretty-printing and cURL export.

The inspector is a native Jetpack Compose screen, not a Flutter overlay: capture and redaction stay pure Dart behind a platform interface, so the debug UI never ships as app surface. Capture is debug-gated — release builds are inert.
